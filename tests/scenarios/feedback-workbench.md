# 场景清单 — 反馈处理工作台 V2

域缩写：`FWB`。机制规范见 [README.md](./README.md)。

范围：反馈从 Issue 创建、事件驱动分发、AI 分析/实现/验证、等待人工补充、结果回写到关闭的完整闭环。
不包含甘特图业务功能本身的正确性；具体功能修复仍由对应业务域场景负责验证。

## 例外队列

- `EXC-FWB-001`：Self-hosted Runner 与 `local_required` 的实际执行属于 Phase 4。Phase 0～3 只需验证其不会误分发并能进入人工处理；Phase 4 分支可保持 `manual`，不阻塞 V2 首期完成。
- `EXC-FWB-002`：邮件、短信、IM 等外部通知不在 V2 首期；`needs_human` 依赖用户保存并回访 Issue capability 链接。若产品要求主动触达，需另立通知、同意与退订合同。
- SDK Runner 原生会话续接、实时 token/tool 流以及个人桌面交互不属于 V2 首期，待官方 Action 路径验证不足时再立项。
- `EXC-FWB-004`（2026-08-16 已拍板）：会话续接失败时（provider session 丢失）应退回重放模式静默继续，还是显式告知用户"上下文已重置"？**结论：显式告知，并把控制面已记录的全部上下文交给新会话。两件事必须同时做到，只做其中一件都不算满足本条。** 理由：静默退回会制造"Agent 突然忘事"的不可解释体验——用户看到的是同一个对话线程，却发现对方不记得三分钟前商定的事，这比一条噪音消息更消耗信任；而只播报不重新播种，等于把恢复成本转嫁给用户重述一遍。**由此产生的架构约束（不是可选实现细节）**：控制面必须持有足以重建上下文的记录，provider session 只是加速器而非事实来源，因此会话表必须持久化上下文快照，执行器必须有一条"从控制面记录播种新 thread"的路径。M0-V6 的文档核对独立印证了这条——Claude Agent SDK 官方文档对跨主机恢复的建议原文是 _"Don't rely on session resume. Capture the results you need (analysis output, decisions, file diffs) as application state and pass them into a fresh session's prompt. This is often more robust than shipping transcript files around."_ 验证点在 M3-T1 并入 `SCN-FWB-034`。
- `EXC-FWB-005`（2026-08-19 已拍板）：`POST /api/feedback` 无任何鉴权（仅有大小限制，见 `workers/share-worker.js` 的 `/api/feedback` 分支），站点 `gantt-task-editor.pages.dev` 带 sitemap、robots、四语言与 Google 站点验证被公开索引，生产库自 2026-05-31 起已积累 23 条 `manual` 与 3 条 `auto_error` 提交——这是否构成 §S-G 条件 1「反馈入口对非你本人的真实用户开放」，从而要求执行器先迁入容器化隔离环境？**结论：不构成。执行器在日常开发机、当前用户身份下运行，容器化不是 M3 的前置条件。** 其余两条 S-G 条件（启用 `auto_deliver`、接入第二个目标项目）与 S1～S5 全部照旧生效，任一触发仍须先迁隔离环境。**已知残留风险（记录在案，不因本条拍板而消失）**：V3 计划 §1.1 自陈这一形态违反 Spec §18.2「Self-hosted Runner 不得与个人日常开发资料、SSH Agent 或浏览器配置共享环境」，因此 S1（独立 checkout 目录）、S2（专用 fine-grained PAT）、S3（读取路径拒绝清单）是仅存的补偿措施，不得再降级。
- `EXC-FWB-008`（2026-08-29 **已拍板：维持多 worker，改的是测试不是并发度**；M6 金丝雀 #5 发现，实录 `run_b8644047`）：写入型 Run 的浏览器验证该用几个 worker？**结论：worker 数不是病因，`--workers=4` 保留。**实测推翻了「降 worker 数能救」的假设——`performance.spec.js:241` 的墙钟阈值在 **1 worker 完全串行**下重复 4 次仍失败 2 次（90.0 / 119.5 / 92.5 / 105.5 ms，阈值 100ms 正压在均值上）；真因是该阈值在**有头**模式下标定（64/77ms）而门禁跑**无头**。另一条 `gantt-features.spec.js:35` 是与应用自排重绘的竞态，同样与并发无关。落地见 `tests/scenarios/gantt-ui.md` 2026-08-29 变更日志（`gotoApp` 统一、`waitForGanttSettle`、`expect.poll`、`server.warmup`、阈值按无头重标定）。全量对照 248 条 / 4 worker / `--retries=0`：master 挂 2 → 改后挂 0。**附带查实**：e2e 不能改跑构建产物——`ai-undo` / `bug-fixes` / `mobile-responsive` / `reproduce_sort_bug` / `row-reorder-hierarchy` 共 16 处在浏览器里 `await import('/src/...')` 取应用内部模块，那是 dev server 专有的源码 URL，换 `vite preview` 会确定性打死 11 条。
- `EXC-FWB-007`（2026-08-29 **已拍板：(b) 合并**，用户授权 AI 按最佳实践细化；M6 金丝雀 #2 发现，实录 `run_0dd5247e`）：`runtime_approval` 卡活跃期间，同一 Issue 的其他 waiting_human 类卡会撞「每 Issue 单活跃卡」唯一索引，且 Worker 报错匹配未认出 D1 实际文本、把 409 语义误报为可重试 500——首个 attempt 投递链死在半路，靠 Run 复用 + 幂等 eventId 在 attempt 2 自愈。**结论（SCN-FWB-045 落地）**：通知与决策分离——M4 之前的拒绝是既成事实（fail-closed 已拒、`allowed_return_states` 为空的卡无法解决），是**通知不是决策**，不配占决策卡坑位。被拒上报降级为 `approval.denied` 内部时间线事件（幂等、聚合），真正建卡的点（waiting_human / run.failed 处置卡）自动携带本轮被拒聚合清单作证据；mid-run 不再翻 Run/Issue/Workflow 状态（Run 还在跑却翻 waiting_human 是时序谎言）。撞卡从机制上消失；报错匹配同时加固（UNIQUE + 表名同现 → 确定性 409）作纵深。M4 落地实时审批时再升级为「卡 + 决议下行」。幂等 eventId 的「attempt 2 回答被去重」副作用随撞卡根因消失而不再可达，不另行处置。
- `EXC-FWB-006`（2026-08-22 已拍板，用户授权 AI 自主决策）：executor 项目的自治交付要不要继续要求 Worker 侧的 GitHub 派发/合并/部署凭据？**结论：不要，Actions 口径在 executor 路径上全部删除。**换成 Worker 真能核验的等价物：项目交付配置完整、`FEEDBACK_EXECUTOR_TOKEN` 存在、执行器此刻在线（心跳在租约上限内）。理由：这三项凭据在 executor 路径上既不被读取也不构成任何保证，留着只会让「配齐了却仍降级」变成常态，并诱使人把凭据配到用不上的地方。执行器侧的凭据边界由启动准入（`executor/admission.js` 的 S1～S3）负责，不由 Worker 代为断言。（2026-08-27 后续：GH 执行路径整体退役，「actions 路径三项凭据检查原样保留」随路径一并删除，本例外就此结清。）
- `EXC-FWB-003`（2026-08-09 已拍板，用户授权 AI 自主决策）：中大型 Issue 如何从只读分析走到实现。**结论：走 (b)，但用既有的 §16.4 Design 闸，而不是新加"直接批准实现"的旁路。** 只读分析 Run 的交付物本身就是结构化 Design，管理员批准 Design 即解锁 `implement_and_verify`。理由：(c) 让 owner 自助升级违反职责分离——提交者常常是匿名用户，改动的批准人不能是请求人，§7.3 的管理员闸保留；(a) 维持现状是活锁——Design 只能由 `agent.waiting_human` 产生，而两个 provider workflow 从来不发这个回调，所以 Design 闸在生产上根本无法到达，`requiresDesign` 的 Issue 会永远在 `analyze` 里打转；纯粹的"管理员一键改成实现"则会让实现在没有商定验收标准的情况下开工，等于废掉 §16.4。选定方案同时也是 Spec 自己的原意——§7.2 注释写明"Agent 只能通过 `agent.waiting_human` 建议改变 policy"。
